# Rally — demonstration walkthrough

Confirmed track: **Indie Developer**. Source of rules: [user-supplied event guide](hackathon-participant-guide.md). The video is three minutes and must clearly identify work created during the hackathon. The demo should show the functioning product, supported by code and a live product. The recording should identify the demonstrated release and separate live operation from test controls.

## Product scenario

“Rally helps a team leave a meeting with a decision and an owner, then shows exactly what was agreed.”

Use a real short English meeting with three consenting participants deciding one concrete software release issue. Prepare the scenario and roles, but let the running product process actual speech. State that this is a rehearsed demonstration; preparation is not a substitute for actual model execution.

Do not try to show an entire 30-minute meeting. Show a compact full decision loop and a separately labeled later-meeting wrap-up checkpoint. The demo clock is a test control; label its use and the actual elapsed time. Preserve ordinary processing speed during the key live intervention.

## Three-minute storyboard

| Time | On screen and audible | Evidence conveyed |
| --- | --- | --- |
| 0:00–0:15 | State user/problem and Indie hackathon contribution. Show Rally's agenda and intended decision. | Clear impact and original contribution |
| 0:15–0:30 | Names/agenda already entered; show consent and Rally's brief opening. | Real setup, recognizable moderator role |
| 0:30–1:10 | Participants discuss release scope, then an off-agenda topic in the labeled rehearsal scenario. Rally redirects at normal speed with a concise prompt. Show actual measured turn-to-intervention timing. | Observed live moderation behavior |
| 1:10–1:45 | Participants make a release decision and propose a follow-up. Rally asks for missing owner/date, gets explicit confirmation, and displays evidence-linked outcomes. | Accountability, bounded autonomy, useful output |
| 1:45–2:00 | Demonstrate host pause/dismiss/override and immediate output stop. | User control and engineering craft |
| 2:00–2:20 | Clearly label “demo clock advanced to five minutes remaining”; trigger actual scheduled wrap-up and read unresolved items. | Scheduled wrap-up with the clock advance explicitly labeled |
| 2:20–2:30 | Show saved evidence, a confirmed WhatsApp follow-up preview and the actual model roles. | Durable value, traceability and clear model attribution |
| 2:30–3:00 | Present the future meeting-platform direction with an explicit future label, then return to the real product and project links. | Product direction grounded in the demonstrated workflow |

If the compressed clock risks ambiguity, show wrap-up in a second clearly labeled short capture instead. Use honest transitions between scenes. Do not accelerate model response time or pass synthetic/precomputed responses off as live. Label replay/fallback footage and disclose which optional integrations are not implemented.

If Teams passes its join/receive/speak gate before feature freeze, use it as the meeting surface or show a brief real participant-join proof. Otherwise use a device-verified room microphone or meeting browser tab. WhatsApp Web is the first Meta preset; Zoom Web, Meet and Jitsi use the same host-selected tab-audio path. Run Check audio before recording. Do not claim browser room capture is a working remote-meeting bot.

## Validation requirements

The demonstration should establish the complete meeting lifecycle: consent, finalized transcript, an agenda-related intervention, an explicitly confirmed decision and owned action, immediate host control, saved evidence, and export. Show the actual model roles and observed timing. Identify unsupported or incomplete paths separately.

Use three consenting participants and record the tested device/network configuration. A clearly labeled scripted walkthrough is useful for exploring controls; live operation requires actual model processing. Keep the intervention footage at normal speed and label clock advances, separate captures and replay footage.

## Rehearsal and submission checklist

- Use newly built code/features only in the claimed hackathon contribution; document external libraries/services and any existing assets honestly.
- Measure response times through the [latency protocol](latency-test-plan.md) before writing latency claims into narration.
- Rehearse at least three complete runs on the chosen device/network; record failures and fix the recurring cause.
- Keep the key intervention sequence at normal speed. Check intelligibility of all three human voices and Rally.
- Show confirmation and source evidence rather than only polished summary text.
- Use a disclosed clock advance to the five-minute wrap-up checkpoint. Default real-meeting wrap-up remains five minutes.
- Fit the final video within three minutes. Check the supplied video link without being logged in.
- Public repository, accessible live product/video, all contributors listed, Representative appointed, Indie track selected, and one project submission.
- Freeze November 3; submit November 4 before 9 PM EST, with buffer for upload/access issues.
