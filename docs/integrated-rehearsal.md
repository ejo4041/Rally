# Integrated Rally rehearsal packet

The current target is the [private Node/LiveKit app](integrated-deployment.md), not the earlier Sites preview. Run a human rehearsal before recording. Automated tests verify lifecycle, audio transport and real local MMS browser playback; they do not establish physical audibility, remote platform compatibility or speaker identity quality.

## Free preparation

1. Connect Tailscale and open the app in the intended Chrome/Edge laptop browser. Sign in with an app account. Do not put credentials or private meeting URLs in the recording.
2. Inform everyone and obtain consent before any capture. In a prepared meeting, use **Check audio · free**. A remote participant speaks while the host is quiet; then the host speaks. Check each source separately. Use headphones for a call. Stop the check and confirm sharing closes. This does not start Muse.
3. Use **Test voice · free**. Confirm a person can actually hear the sentence, then stop it mid-sentence. This is host-browser playback. A remote listener must separately verify any intended call-side audio-sharing arrangement; it is not provided automatically.
4. Confirm no previous live meeting needs to be ended. Have a backup microphone and a rehearsed room-microphone surface available if tab capture fails. Do not switch to a platform's built-in transcript as a substitute for Muse.

## Consented live run

Creating/preparing a plan, starting Muse transcription, requesting guidance and final analysis incur normal provider charges. Review the existing app usage and budget gates first. Use one short run and reconcile its actual usage before repeating.

| Step | Action | Observe |
| --- | --- | --- |
| Prepare | Objective: decide Friday release readiness and rollback-check ownership. Enter the actual speakers. | A useful generated agenda; duration/topic budgets make sense. Roster names have not identified voices. |
| Capture | Start with consent. Each person says one distinctive sentence. | Finalized text matches the content; partials remain temporary; missing/ambiguous speakers stay uncertain. |
| Attribute | Assign a recognized speaker label, clear it, then restore the correct name. | Transcript updates; no model request from label editing; session labels remain distinct after reconnect. |
| Guide | Discuss an off-agenda topic, then return to the release decision. Use Ask Rally only if deliberately demonstrating a host-triggered request. | Actual prompt, evidence/progress and ordinary response timing. An irrelevant/missing prompt is a finding, not a cue to replace it in the footage. |
| Speak | Enable spoken prompts and allow a relevant approved prompt. | Audible host-side MMS voice. During playback, shielded input is clearly shown. Stop restores listening; mute stays muted if it was already selected. |
| Override | Pause, resume and dismiss. | Audio stops immediately; older results do not resume speaking. Transcription continues during moderator pause. |
| Clarify | “Release after rollback is verified.” “Priya will check rollback Thursday at three.” | Actual spoken owner/date are retained. Do not infer an unspoken commitment. |
| Finish | End, wait for report, navigate away and reopen. | Capture stops; final words survive; report appears once ready. Review an outcome's linked source and unresolved details. |
| Correct | Change a label after report generation. | Existing report is marked as using older labels. Reanalysis is explicit and charged; skip another model call if unnecessary. |
| Preserve | Add a host correction note, export, then reopen history. | Saved evidence and corrections persist. Remove synthetic test records when no longer needed. |

Record actual devices, selected call surface, who heard the voice, response-time definitions, transcript/name mistakes, any failure and actual usage. Do not save private audio or participant names in public engineering notes without their permission.

## What to record for the demo

Use [the three-minute script](demo-script.md). Lead with a complete useful decision loop and close with the future platform idea. The integrated report uses model interpretations, not a mandatory host-confirmation workflow. Presenter mode, a demo clock and the older confirmed-outcome sharing workflow belong to the Sites release. The integrated [WhatsApp draft](integrated-whatsapp-follow-up.md) uses host-selected report interpretations and manual editing. Do not narrate controls that are absent from the demonstrated release.

## Remaining access work

The integrated deployment requires Tailscale and app authentication. Decide and test a judge-access route before final submission; a private server URL alone is insufficient. Keep final submission, visibility changes, contributor verification, source-license choice and video publication pending for the user.
