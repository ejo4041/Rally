# Rally frontend for the Node backend

The authenticated frontend for `apps/rally-api`. It uses the backend's real HTTP and LiveKit contract; it does not use the separately hosted Sites Worker's routes. Source is TypeScript with the browser LiveKit SDK and a small esbuild build. No provider keys are included in the frontend.

## Run locally

From the repository root, with Node 24+ and npm on PATH:

```bash
npm ci --prefix apps/rally-api
npm ci --prefix apps/rally-web
cd apps/rally-api
npm run setup:media
cd ../..
node scripts/dev-rally.mjs
```

Open `http://127.0.0.1:5173`. Create an account or use previously seeded demo credentials. The launcher starts the API/media server and frontend, proxies `/api` to the API with cookie sessions, and stops its owned processes on Ctrl+C. It explicitly defaults paid processing off. Real agenda/transcription/report calls require an intentional `RALLY_PAID_ENABLED=1` environment setting and the existing shared server-side configuration. Follow the [budget policy](../../docs/api-budget.md) before real experiments.

With paid processing off, accounts and history work; meeting creation saves a draft with a visible preparation error. There is no fake model output or automatic paid fallback. The host can edit a plan manually, but starting transcription still requires enabled provider access.

`RALLY_WEB_PORT` changes the frontend port. `PORT` changes the API port; `LIVEKIT_PORT` and `LIVEKIT_BINARY` configure the backend's media launcher. `RALLY_API_URL` overrides the local HTTP proxy target. Separate worktrees should use separate databases and available ports. The frontend development server binds loopback. It is a local development setup, not a remote deployment recipe.

If the API is already running, use `npm run dev` from this package. Production assets are generated by `npm run build` in `dist/`; deployment needs an authenticated API proxy and reachable TLS/WebRTC media configuration. Do not put model keys or LiveKit server secrets in browser configuration.

## Implemented workflow

October 30 additions: [free local audio check](../../docs/audio-preflight.md), [opt-in host-browser MMS/free voice test](../../docs/integrated-speech.md), [reversible session speaker labels and stale-report handling](../../docs/speaker-attribution.md), durable host correction notes and [reviewed manual WhatsApp drafts](../../docs/integrated-whatsapp-follow-up.md). Speech is host-side; remote call audibility needs rehearsal.


- Sign up, sign in/out, owner-isolated history and session-expiry cleanup.
- Prepare an agenda with Muse, inspect/edit objective, topics, status and budgets before recording; preparation failures remain visible and retryable.
- Consent-gated microphone or meeting-tab audio with optional host microphone. Permissions are acquired before asking the backend to start a model session. Partial/canceled selections close tracks; stopping sharing ends capture and asks the backend to finish the meeting.
- Real LiveKit publication under the backend's host identity. Finalized transcript updates upsert by turn ID/revision; partials stay transient. Speaker corrections use session-scoped keys, preserving unknown identities.
- Server-approved intervention events, health/concerns/progress, announced plan revisions and original-plan history. Host mute, pause/resume, dismiss, explicit guidance and end controls.
- HTTP snapshots on reconnect, event-triggered refresh and polling fallback. A normal page reload can attach to the existing room without starting another ASR session. A capture gap stops local audio and offers explicit new-session restart; labels restart.
- Asynchronous report processing/ready/failed, explicit paid retry, nullable scores with coverage, outcome status, evidence navigation, speaker tips, host correction notes, export and deletion.
- Recorded usage and unknown/pending requests; this is not a verified Billing balance.

A single microphone publication is accepted by the backend. Meeting-tab and optional microphone sources are mixed into that track. The user joins WhatsApp/Zoom/Meet/Jitsi normally; this is host-side capture, not a participant bot or automatic platform name import.

Reports use the new backend's `reported_agreement`, `proposal` and `unresolved` semantics. No host-confirmation workflow is added. Scores and tips are model interpretations, and voice labels are not verified identities.

## Checks

```bash
npm run typecheck
npm test
npm run build
npm run test:browser
```

The browser integration test also requires the backend dependencies, Playwright Chromium and the local LiveKit binary installed by `setup:media`. `RALLY_TEST_LIVEKIT_BINARY` can point to an existing binary. On hosts with separately installed browser libraries, supply `LD_LIBRARY_PATH` as needed.

Tests start a real isolated Express API, SQLite database and LiveKit server, then use the actual frontend and cookie session in Chromium. Audio is synthetic; model providers are deterministic injected fixtures. The fixture's `/api/test/*` routes exist only in `tests/fixture.ts`, never in the production API. Tests do not load shared secrets, contact Meta or join an external platform. A separate fixture account checks owner isolation. Owned servers/browsers/database are removed on completion.

The report fixture intentionally fails once to exercise explicit retry. Its outputs are labeled test evidence, not measured model quality. Unit tests additionally exercise stale snapshot/revision/control ordering. [Validation and limitations](../../docs/frontend-integration.md).

## Teams meeting links

The Meetings page includes the existing three-minute Teams transcription-test flow: paste an invite, consent, admit Rally, inspect lobby/live status, Leave and save finalized text to your own history. This is separate from live browser moderation. Other platforms use the clearly explained call-tab path. [Details and service configuration](../../docs/teams-integrated-ui.md).

## Remaining work

Remote deployment, physical microphone/speaker behavior, real multi-person/room attribution and a complete human rehearsal remain unverified. Generated moderator speech is a subsequent backend integration; subscribing to an audio track does not provide TTS. Existing Sites features such as its free local audio meter, presenter view and WhatsApp sharing remain in that separate app. No final submission has been made.

To exercise actual local MMS in the browser fixture after provisioning, set `RALLY_TEST_REAL_MMS=1 RALLY_MMS_ENABLED=1` when running `npm run test:browser`. Reasoning/ASR remain deterministic injected fixtures; no paid model request is made. The default speech fixture is a synthetic WAV.
